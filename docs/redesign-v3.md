## Stack
- Plain HTML, CSS and ES modules. No build step.
- GSAP 3.15.0 (core, ScrollTrigger, SplitText) and Lenis 1.3.26, served from assets/vendor. Lenis 1.3.27 was skipped because it was three days old. ScrambleText is no longer loaded (the decode effect is now opacity only).
- Type (revised 2026-10-18 at the client's request for lighter, more futuristic headings): Mona Sans, self-hosted variable font. Headlines in its Expanded width (125%) at weights 330–380; figures at 320; titles at 500 and 112.5% width; body at normal width. Geist Mono for labels, IDs and data. Chosen from a side-by-side of Mona Sans, Hubot Sans, Archivo, Saira, Unbounded and Michroma; the wide forms echo PROTECT in the logo.
- Futuristic system details: guide hairlines with crosshairs at section seams (desktop), viewfinder corners on product surfaces (zoom card, match board, stage, calculator), a faint dot matrix on dark panels, mono uppercase navigation, and labels and IDs that decode into place behind a block caret.
- All fonts and scripts self-hosted (assets/fonts with OFL licences, assets/vendor). No third-party requests at runtime, except the booking page, which loads the client's GoHighLevel form (2026-10-23).
- Three.js was considered and not used: the product's truth is records and matches, which read best as crisp DOM/SVG; WebGL would add weight and GPU cost on site-office laptops without improving comprehension.

## Motion system (2026-10-19)
- **One spring.** Stiffness 180, damping 22, mass 1: ζ 0.82, 1% overshoot (cap was 3%), settles in about 0.65 s. `--spring` in CSS (sampled `linear()`, cubic-bezier fallback) and `spring` in GSAP (js/motion.js) are the same curve. Its critically damped twin (`--spring-soft` / `springSoft`) is used for opacity, digits and pointer follow; `springIn` (its mirror) for exits in the scrubbed hero. Ambient loops use `--harmonic` (undamped oscillation). No linear, default, bounce or elastic easing anywhere; the old 5% and 20% overshoot curves are gone.
- **Entries** (js/engine.js). One IntersectionObserver band: an element plays once it is 25% into the viewport. It plays at most once per scroll direction: it resets only when fully off screen, and only if the direction it will return from has not played yet. Elements arriving together are staggered 80 ms apart in document order (span-aware for multi-line headlines). Anything still waiting in view plays when scrolling stops (600 ms) or at the end of the page. Focusing something that has not played plays it.
- **Order.** Label (index first, then the words decode) → headline lines → copy → actions. Conclusions wait for their evidence (the gap's £1,008 waits for the zoom; the scan view's readings follow the scan).
- **Durations.** Sequences 0.8–1.4 s, never over 2 s; hover and press 0.22 s; major reveals at least 0.45 s.
- **Transform and opacity only.** Colour, shadow and background changes are pseudo layers that fade; bars that change size are fixed elements scaled (nav indicator, step dots); wires are revealed by a scaling clip; the gap zoom scales the data layer and counter-scales stripes, edge and ruler labels; the FAQ uses FLIP instead of animating height. No permanent `will-change`; GSAP promotes during tweens and releases after.
- **Ambient** (only while the section is on screen, via `[data-live]` → `.is-live`): hero label ring, dot-matrix drift on dark panels, gap edge luminance, match connector wave, leak flag rings, stage scan pass every 4.8 s.
- **Reduced motion.** `prefers-reduced-motion: reduce` (or `?motion=reduce`, which adds `.rm`) renders every finished state immediately: `animation: none` and `transition: none` everywhere, no pins, no idle loops.

## Preloader (2026-10-23)
- **What it does.** The first visit in a session opens on a dark field with the shield as a faint silhouette. A lime scan line rises through it and lights it from the bottom as the page really loads (the hero film's opening frames, then the fonts), with a mono count, "Verifying 047". At 100 the count becomes a tick and "Verified" and a ring leaves the shield. Then the panel lifts like a gate arm with the scan line on its lower edge, the shield flies onto the shield in the nav logo (measured, so it lands to the pixel) and hands over to it, and the hero intro starts as the headline is uncovered. It replaced the small loader that sat inside the hero.
- **Honest timing.** It shows real progress and is never faster than 1.1 s from navigation, so a fast load does not flash; it finishes by 4 s whatever is still loading (the hero's own 1.5 s fallback applies too). A script that arrives after 5 s just fades it. About 2.8 s end to end on a good connection.
- **Never in the way.** Once per session (sessionStorage `pp:intro`), never with reduced motion, and never without JavaScript. The class is set in the page head with its own 7 s timer, and a CSS animation fades the loader at 7 s, so a failed script can never leave the page covered. Before any script runs, CSS alone starts the light rising (a registered `--p`), so a slow connection never shows a frozen loader. Scroll is held while it shows; the scrollbar space is kept (`scrollbar-gutter: stable`) and painted dark, so nothing shifts when it goes.
- Files: js/loader.js, the Preloader block in css/base.css, assets/brand/mark-256.png. QA handle: clear `pp:intro` in sessionStorage to see it again.
- **Stale caches (fixed 2026-10-23).** After a deploy, a browser kept an old base.css under the new page and the loader's markup showed raw. Three layers now: the loader is `display:none` in its own markup (CSS shows it with `!important`), so missing or stale CSS can never show it; every stylesheet and script is versioned by content (`?v=<hash>`, and an import map so every module and its imports are versioned too), written by `node tools/stamp.mjs`; and .htaccess makes browsers revalidate pages, styles and scripts on each visit. **After changing any CSS or JS, run `node tools/stamp.mjs`**; tools/check.mjs fails while a page is out of date.

## Scroll language (2026-10-19)
Extended from the matching scene to the whole page at the client's request: "scroll animations ... premium, futuristic, minimal".
- **Headlines light up with scroll.** Every section headline (and the footer line) starts dim and brightens word by word as it scrolls into reading position (scrubbed: top 88% to top 45%), so the light follows the scroll both ways. The hero headline keeps its intro. Non-breaking spaces stay inside their word (js/reveal.js `lightUp`).
- **Leaks pin and play.** On desktop the section pins (2.4 viewport heights) and the three leaks take turns, one card at a time, entering from below and leaving upwards. Within its turn each card's evidence check is scrubbed by scroll, and a stepper (01–03) fills as you go. On smaller screens each card's check plays as the card scrolls up the screen (js/leaks.js).
- **Leak instruments.** Each card is a light instrument (dark cards read as too much contrast on a light section, so cards on light sections stay light): a panel with a faint grid, thin lines and mono readings above a white body. Green marks a valid scan, amber a discrepancy; thin strokes and small text use the ink variants (#B47B00, --amber-ink, --lime-ink) to hold contrast on white. Ghost workers: a scan of light with a short trail crosses the week and each day comes back empty. Inflated hours: the claim is drawn, then the gate record; dashed guides carry the gate times up to the claim and the overrun grows outward from them. Proxy clocking: a ping at gate 1, a signal travels to gate 2, a second ping, then the 1 s bracket. A finished check warms the panel with a low amber wash. Without the scene (reduced motion, no script) the three cards sit side by side under the heading, finished.
- **One card language on light sections (2026-10-19).** The same light instrument style runs through every card on a light section: the gap zoom card (grid panel, mono header with a live zoom factor ×1.0 to ×20, grey claimed bar, green gate bar, amber hatch for the unverified hours, amber wash once zoomed); the How it works stage (grid panel behind each view, thin green timesheet bars on a 06:00 to 19:00 axis, the invoice line against the gate record as two bars with a guide and the overrun in amber, amber bars per exception type, a green and amber split for the payment run); and the governance flow (a schematic on a faint grid, numbered nodes with status lights that turn green as each node lights, green packets, the export node closing with a green edge). Dark surfaces remain where the section itself is dark (the hero, the matching stage, the booking section) and on the numbers panel, which was tried light and switched back to dark at the client's request.
- **The numbers read as a sum.** The four figures light in sequence with scroll and count up as they light: £82bn × 1.7% = £1.4bn, then 2.1m workers (operators shown on wide screens). Scrolling back dims them and counts down (js/scrubs.js).
- **Governance and pilot draw with scroll.** The data flow lights node by node; the lifecycle chart and the 90-day chart draw as they scroll into view and undraw on the way back. The pilot figure counts up once the line reaches day 90.
- **How it works follows the reading line.** Step opacity tracks the distance from a reading line 60% down the screen, and each step's top rule fills as the line passes through it.
- Reduced motion: every headline lit, every figure and chart final, no pins.
- Fix found while testing: Lenis is re-measured on every ScrollTrigger refresh, so smooth scrolling never clamps to a stale end of page when pin spacing changes the page height.

## Smooth film playback (2026-10-21)
- **Cause.** Both scroll films (the hero and the orbit film) drew each frame from a plain image. The browser decodes such an image on the main thread as it is drawn, 50–80 ms for a 1600 × 900 frame on a laptop, and its cache cannot hold all the frames, so scrolling stalled every time the film moved on a frame. A trace of one 8-second scroll through the hero showed about 3 s of decoding on the main thread.
- **Fix** (js/frames.js, used by js/hero.js and js/film.js). Frames are fetched compressed and decoded off the main thread with createImageBitmap: ten ahead of the playhead in the direction of travel, four behind. Frames further away are freed, about 86 MB held for a 1600 × 900 film. Each film frees its frames once scrolled past and decodes them again on the way back, keeping the picture on screen meanwhile. The first frame's preload is now `as="fetch"`, so the fetch reuses it.
- **Continuous motion.** The films blend the two frames either side of the playhead, so the picture moves smoothly however slowly the page scrolls. Before, a gentle scroll showed the film at about 18 frames a second.
- **Measured** (headless Chrome, Intel UHD laptop, 8 s steady scroll through the hero). First scroll: 95th-percentile frame 50–73 ms before, 17–19 ms after. On a return visit no frame goes over 25 ms. At 4× CPU slowdown, frames averaged 300–500 ms with freezes of a second or more before, 23–28 ms after. One hitch remains: about 0.4 s on a browser's very first visit, a GPU shader compile as the section below the hero comes into range. Chrome caches it, so it happens once.
